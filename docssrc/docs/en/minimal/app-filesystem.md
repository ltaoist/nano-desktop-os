# Apps and Data

## App type detection

The app manager identifies two app types by directory-name suffix, in `get_app_type()` and `get_executive_file()`:

| Suffix | Type | Entry file | Description |
|------|------|----------|------|
| `.App` | `"app"` | `{name}.App/main.py` | full app, includes a frontend page (index.html) |
| `.py` | `"script"` | `{name}.py/{name}.py` | script app, no separate frontend page |

The app list is generated by scanning `Data/AppData/` in real time on each `list_apps()` call; no persistent index is maintained. The functions related to `Data/System/apps_index.json` are defined but currently unused.

**icon field**: the app icon is the capitalized first letter of the directory name (e.g. calc.App → "C"), a minimal icon scheme.

## App content serving

The frontend of an `.App` app is served through three routes:

**`GET /app-content/{app_name}`**: redirects to `/app-content/{app_name}/`, ensuring the browser resolves relative paths in directory form.

**`GET /app-content/{app_name}/`**: the core route, which does one key thing — injects THREAD_ID:

```python
with open(index_html, "r", encoding="utf-8") as f:
    html = f.read()
html = html.replace("</head>", f'<script>window.THREAD_ID="{thread_id}";</script>\n</head>')
return HTMLResponse(html)
```

It reads the app directory's `index.html` and inserts a `<script>` that sets `window.THREAD_ID` before the `</head>` closing tag. This is HTML-string-level injection that requires no cooperation from app code. `nano_tob.js` reads this global variable after it loads.

**`GET /app-content/{app_name}/{path:path}`**: serves static resources (CSS, JS, images, etc.) from the app's `static/` subdirectory. Note that the static file path is `{app_dir}/static/{path}`, so app images and extra scripts must be placed under `static/`.

### Where nano_tob.js is served

The `<script src="/nano_tob.js">` script is not in the backend routes; it is served by the frontend Vite dev server from `src/frontend/public/nano_tob.js`. In development mode (port 5173), the iframe's `/nano_tob.js` request is intercepted by Vite and returns the file in the public directory. After a production build, the frontend dist directory must be mounted to the backend (the current version relies on the Vite dev server).

## Install mechanism

`install_app(source_path)` supports three sources:

1. **.zip file**: `zipfile.ZipFile` extracts to `Data/AppData/{real_name}/`. The ZIP root must directly contain the entry file (no extra nested directory). Only zip is supported, not rar/tar.gz.
2. **Directory**: `shutil.copytree()` copies the whole directory to `Data/AppData/`.
3. **Single file**: creates a `Data/AppData/{filename}/` directory and copies the file in with `shutil.copy2()`.

After installation it calls `get_executive_file()` to verify the entry file exists; on failure it deletes the copied directory and returns an error. `force_install_app()` deletes the same-name directory first and then installs, implementing overwrite installation.

## Data storage framework

`data_storage.py` implements app-private storage; the core design is **filesystem-path storage isolated by app name**:

```
Data/AppDataStore/{app_name}/
└── _pathstore/           # path data storage root
    ├── config.json       # /config.json → _pathstore/config.json
    ├── leaderboard.json  # /leaderboard.json
    └── subdir/           # /subdir/ → _pathstore/subdir/
        └── data.txt
```

Paths start with `/`; `_sanitize_path()` removes the leading `/` and maps to a filesystem path under `_pathstore/`. `os.makedirs(os.path.dirname(target), exist_ok=True)` creates parent directories automatically.

**Path vs file**: `listAppPathEntries` can list directory contents; `getAppPathData` returns None for directories and only reads files; `deleteAppPathData` recursively deletes directories (`shutil.rmtree`) and deletes files.

**API design principles**:

- All synchronous functions — file I/O is fast enough in a desktop scenario, no async wrappers needed
- No built-in locks — `data_storage` provides no cross-process locks; apps must handle concurrent writes themselves (like snake.App's file lock implementation)
- No versioning — overwrite writes; apps manage their own data format migration
- `deleteAppDataStore(app_name)` deletes the entire app data directory, used by the "clear data" feature

**System special app name**: thread history data uses the app name `"_system"`, stored at `Data/AppDataStore/_system/thread_history/{thread_id}.json`, fully isolated from user app data.
