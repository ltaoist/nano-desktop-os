逻辑线程编程

逻辑线程编程是 Nano Desktop OS 组织应用运行的编程范式。要理解它，可以从分布式计算的历史线索来看。

1990 年代的 CORBA（Common Object Request Broker Architecture）提出了对象请求代理（ORB）的概念：不同进程、不同语言中的对象通过 ORB 互相调用方法，调用方持有代理对象，调用过程如同本地方法调用。CORBA 的理想是让分布式编程像本地编程一样透明，但它的规范极其庞大复杂，IDL 定义、对象生命周期、命名服务、事务处理等层层叠加，实际应用门槛很高。后来的 RPC（Remote Procedure Call）框架——从早期的 ONC RPC 到现代的 gRPC、Thrift——将问题简化为远程过程调用，去掉了"分布式对象"的重量，聚焦于函数级别的请求-响应，在服务端开发中得到了广泛应用。

逻辑线程编程是在这些基础上对编程视角的一次调整。它的关注点不是"如何调用远程对象的方法"，也不是"如何调用远程函数"，而是将一个正在进行的工作会话本身作为编程的基本单元。每个逻辑线程是一个独立的工作会话，拥有自己的状态、逻辑和界面；用户与线程交互，线程与线程之间通过代理机制互操作，但线程本身不是一个"服务"或一个"对象"——它是一个正在进行的过程，有开始、有交互、有结束。后端进程承载线程的计算和状态，前端页面承载线程的呈现和交互，两者是同一个线程在不同环境中的两面。

这个思想并非全新。许多大型多进程、多线程应用——IDE 中每个打开的项目是一个工作会话、浏览器中每个标签页是一个独立进程、桌面环境中每个窗口对应一个运行中的程序——都在系统层面体现了逻辑线程的思想。但这些系统中，逻辑线程通常是内部实现机制，不暴露为应用开发者面对的编程范式。Nano Desktop OS 将逻辑线程明确为平台的核心抽象：开发者编写的不是一个"服务"或一个"页面"，而是一个逻辑线程的后端和前端，系统负责线程的创建、进程管理、窗口管理和前后端互操作。

TOB（Thread Objects Broker）的命名正源于此——它是线程对象之间的代理，与 CORBA 的 ORB 有思想上的渊源。
