TOB Server Implementation

The TOB server is embedded in the TOBServer class in main.py, mounted at the /ws WebSocket endpoint. The frontend iframe and each backend subprocess both connect here as WebSocket clients, and the server routes method calls between them.

Connection model

The TOB server does not distinguish "frontend connections" from "backend connections" — all connections are equal WebSocket clients. The server implements thread isolation via the thread_id field in messages. Unified message format:

{
  "thread_id": "abc123...",
  "id": "Ins-xyz...",
  "type": "messageType",
  "params": { ... }
}
  • thread_id: logical thread identifier; the server isolates TOB namespaces of different threads based on it
  • id: instruction ID (Ins- prefix), generated by the requester, used to match a response back to the original request
  • type: message type, determines which handler _dispatch routes to
  • params: message parameters, structure varies by type

The first message after a connection is established must carry thread_id (the TOB client automatically includes it when it first sends a request after connecting). The server extracts thread_id from the first message and binds it to that connection.

Five core data structures

self._tobs = {}          # tob_id → {"ws", "thread_id", "name"}
self._names = {}         # (thread_id, name) → tob_id
self._pending_calls = {} # proxy_id → (caller_ws, caller_tid, caller_ins_id)
self._tob_waiters = {}   # tob_id → [(ws, tid, ins_id)]
self._named_waiters = {} # (thread_id, name) → [(ws, tid, ins_id)]

_tobs is the TOB object registry. Each TOB object belongs to a WebSocket connection (the ws field), i.e. the creator/holder of that TOB. The server does not store the method list — mountTOBMethod is a purely local operation; the method table lives in each end's TOB._methods dictionary, and the server does not know which methods are mounted.

_names implements name lookup. The key is the (thread_id, name) tuple rather than just name, ensuring thread isolation — thread A's "app" and thread B's "app" do not conflict.

_pending_calls is the routing table. When a caller initiates callTOBMethod, the server generates a new proxy_id (a new Ins- prefixed instruction ID), records "who sent it and what the original instruction ID is", then forwards to the target with proxy_id as the id. When the target returns the result with this proxy_id, the server looks up _pending_calls to find the original caller and sends the result back using the original instruction ID. This makes the caller and callee unaware of each other's existence.

_tob_waiters and _named_waiters are waiting queues. waitTOB/waitNamedTOB add the waiter to the queue when the target TOB does not exist; when createTOB/nameTOB happens, the server iterates the queue and notifies waiters. Timeouts are implemented with asyncio.sleep(timeout/1000) — when it expires, the waiter is removed from the queue and a null result is sent.

Full routing process of a remote call

Take "frontend calls backend's calculate method" as an example; message flow is:

Frontend (JS)                      TOB server                       Backend (Python)
   │                                  │                                   │
   │──callTOBMethod─────────────────→│                                   │
   │  id: Ins-A                       │                                   │
   │  params: {tob_id: Tob-X,         │                                   │
   │          method: "calculate",    │                                   │
   │          params: ["1+2"]}        │                                   │
   │                                  │  1. generate proxy_id = Ins-B     │
   │                                  │  2. _pending_calls[Ins-B] =       │
   │                                  │     (frontend ws, tid, Ins-A)     │
   │                                  │──callTOBMethod─────────────────→│
   │                                  │  id: Ins-B                        │
   │                                  │  params: {tob_id: Tob-X,         │
   │                                  │          method: "calculate",    │
   │                                  │          params: ["1+2"]}        │
   │                                  │                                   │ 3. look up _methods["calculate"]
   │                                  │                                   │ 4. execute function, get result
   │                                  │←─callTOBMethodReturn────────────│
   │                                  │  id: Ins-B                        │
   │                                  │  params: {result: "3"}            │
   │                                  │                                   │
   │                                  │ 5. _pending_calls.pop(Ins-B)     │
   │                                  │    → (frontend ws, tid, Ins-A)    │
   │←─callTOBMethodReturn────────────│                                   │
   │  id: Ins-A                       │                                   │
   │  params: {result: "3"}            │                                   │

Key points:

  • The server generates a new instruction ID (proxy_id) for each cross-end call, isolating the two ends' instruction namespaces
  • Method lookup and execution happen entirely on the receiving end; the server only forwards and does not validate methods
  • If the receiving end's TOB does not exist or the method is not mounted, the receiving end returns an error and the server forwards it unchanged

Connection cleanup

When a WebSocket disconnects (page closed, subprocess exited), the _cleanup method does:

  1. Iterates _tobs, finds all TOBs held by that connection, deletes them, and clears name bindings
  2. Iterates _pending_calls, deletes entries where that connection is the caller (the callee's return would have no receiver, but correctness is not affected)
  3. Removes that connection's waiting entries from the two waiting queues

Note: if the disconnected end is the callee, the caller receives no error notification — it just waits forever. Applications should handle this with timeouts.

Heartbeat keepalive

The server sets a 30-second receive timeout in the handle method: if no message arrives within 30 seconds, it sends an empty JSON {} as a heartbeat ping. This prevents the WebSocket connection from being dropped by intermediate proxies (such as Nginx) after long idle periods. The Python client (nano_tob.py) uses the websockets library's default heartbeat; the JS client relies on the browser's WebSocket implementation.

Symmetric design of the two clients

The Python client (nano_tob.py) and JS client (nano_tob.js) are structurally symmetric:

  • Both have a TOB class holding an id and a _methods dictionary
  • Both have a _TOBNode/TOBNode class managing the WebSocket connection, the _pending Future/Promise mapping, and the _tobs local cache
  • Both use a _request() method to send requests and create a Future/Promise to wait for the response
  • On receiving a callTOBMethod message, both look up the local _methods dictionary, execute the method, and return the result with callTOBMethodReturn
  • The only differences are that Python uses asyncio Future while JS uses Promise, and Python uses the websockets library while JS uses the browser's native WebSocket
